# Agent 稳定性保障

## 1. 项目要保证的稳定是什么

LLM 的自然语言回答和工具选择具有不确定性，因此本项目不保证同一个问题每次生成完全相同的
文字。项目保证的是：**即使模型的规划发生变化，执行过程仍然被限制在确定的业务边界内，
关键操作不会因为模型失误而无限循环、越权访问、跳过确认或破坏数据。**

当前稳定性控制链如下：

```text
用户请求
  → Supervisor 受限路由
  → 专业 Agent 在最小工具集内自主规划
  → 工具校验参数和可信身份
  → interrupt 等待必要输入或确认
  → 数据库事务执行最终业务校验
  → SpecialistResult 结构化返回
  → Supervisor 统一回复
```

基本原则是：**提示词引导模型走正常路径，代码负责强制执行不能突破的边界。**

## 2. Supervisor 路由受到硬限制

Supervisor 只能通过五个显式 handoff 工具进入对应的专业 Agent：

- `delegate_to_general_qa`；
- `delegate_to_rental_recommendation`；
- `delegate_to_rental_booking`；
- `delegate_to_order_history`；
- `delegate_to_order_cancellation`。

多意图请求采用串行增量处理：Supervisor 每次提取一个明确任务，专业 Agent 返回结果后，
Supervisor 再根据原始请求和已有结果判断是否需要委派下一个任务。

handoff 工具在代码中强制检查：

- 一次模型响应只能委派一个专业 Agent；
- 单轮最多委派 3 次；
- 同一轮不能重复委派同一个专业 Agent；
- 委派任务不能为空。

不符合条件的调用只会得到 `rejected` 结果，不会执行错误路由。因此“一次一个、最多三个、
不能重复”不是仅依赖提示词的软约定。

每次有效 handoff 都会保存目标 Agent、明确任务、选择原因和 `tool_call_id`。专业 Agent 返回后，
结果写回同一条委派记录，Supervisor 才继续规划。

## 3. 专业 Agent 只有最小业务权限

每个专业 Agent 只注册本领域所需的原子工具：

- 一般问答 Agent 只能搜索、读取网页和分析页面视觉内容；
- 房源推荐 Agent 只能读取偏好、探索市场和查询房源；
- 预订 Agent 只能定位房源、检查档期、请求信息和创建订单；
- 历史订单 Agent 只能查询订单；
- 取消订单 Agent 只能查找订单、检查资格、请求确认和取消订单。

模型可以自主决定工具调用顺序和参数，但无法调用未注册的能力。LLM 不能直接执行任意 Python、
任意 SQL，也不能让查询 Agent 获得写订单的权限。

业务能力拆成原子工具还能避免把固定流程隐藏在一个大工具中。Agent 保留自主规划能力，而每个
实际动作仍通过可校验的代码接口执行。

## 4. 模型和工具循环具有执行上限

`SpecialistBudgetMiddleware` 为每个专业任务记录：

- 模型调用次数；
- 业务工具调用次数；
- 是否进入最后一次结构化输出尝试；
- 是否禁止继续调用模型。

当前模型调用上限统一为 12 次。各专业 Agent 的业务工具上限为：

| 专业 Agent | 业务工具调用上限 |
| --- | ---: |
| 一般问答 | 9 |
| 房源推荐 | 8 |
| 房源预订 | 6 |
| 历史订单 | 4 |
| 取消订单 | 6 |

达到业务工具上限后，中间件会隐藏普通业务工具，只允许模型生成结构化结果。如果模型仍不按
协议结束，或者模型调用次数已经耗尽，代码会直接生成失败的 `SpecialistResult`。

因此模型不能无限执行 `model → tools → model` 循环。任务可能以明确失败结束，但不会无上限
消耗模型和外部工具资源。

一般问答的搜索、网页读取和视觉分析还具有各自的单轮额度。网页读取单次最多接收 4 个去重
URL，并拒绝既非用户提供、也未出现在搜索结果中的 URL，降低重复调用和虚构链接风险。

## 5. 专业 Agent 必须结构化结束

所有专业 Agent 使用统一的 `SpecialistResult`：

```python
class SpecialistResult(TypedDict):
    agent: SpecialistName
    status: Literal["success", "needs_input", "failed"]
    summary: str
    user_facing_answer: str
    completed_tasks: list[str]
    remaining_tasks: list[str]
```

LangChain 根据 Schema 校验结果，并把有效结果写入 `structured_response`。主图随后：

1. 检查专业结果是否存在；
2. 找到最近一条尚未完成的 handoff；
3. 使用 handoff 的真实路由身份覆盖模型填写的 `agent`；
4. 将结果写入对应委派记录；
5. 清空临时结果，防止下一次委派误用旧数据。

Supervisor 因此读取固定的状态、摘要、已完成任务和剩余任务，不需要解析专业 Agent 任意变化
的自然语言结尾。模型即使填写了错误的 Agent 身份，也不能改变实际路由归属。

## 6. 缺少输入时必须暂停，而不是假装完成

需要用户补充信息时，专业 Agent 使用 `request_user_input` 工具。该工具在内部调用 LangGraph
`interrupt`，将当前执行状态写入 checkpoint 并暂停，收到用户输入后从原工具调用位置恢复。

房源推荐、预订和取消 Agent 还安装了 `UserInputGuardMiddleware`，防止模型忘记调用工具、
只用普通文本向用户提问：

1. 如果模型已经生成工具调用，Guard 不介入，避免重复操作；
2. 对普通文本先使用硬规则识别明确缺失字段；
3. 硬规则不能确定时，再使用结构化 LLM 分类；
4. 确认必须等待用户后，将普通回复转换为 `request_user_input` 工具调用；
5. 分类器失败但能识别明确字段时仍进入 interrupt；完全无法确定时记录失败并放行。

取消订单的写工具还有独立的强制确认。`cancel_order` 在工具内部执行 interrupt，只有用户明确
确认后才调用数据库取消。这个保护不依赖模型是否记得询问用户。

## 7. 可信身份和工具参数不由模型控制

`user_id` 不作为普通工具参数暴露给 LLM，而是从可信的运行时 state、context、config 或开发
环境变量中解析。订单读取、搜索和取消在 SQL 层始终附带 `user_id` 条件，模型不能通过修改
参数查询或修改其他用户的订单。

业务工具还会在执行前校验：

- 手机号格式；
- 入住和退房日期；
- 租金预算范围；
- 订单状态；
- 查询数量上限；
- 房源及订单是否真实存在。

工具统一返回 JSON 字符串，通过 `status`、结果字段和 `error` 区分成功、空结果、参数无效、
拒绝和失败。虽然传输类型是字符串，内容是稳定的机器可读协议，Agent 不需要从任意自然语言
中猜测工具执行状态。

## 8. 写操作由数据库完成最终校验

模型对业务状态的判断不能直接作为写入依据。创建预订时，数据库会在
`SERIALIZABLE` 事务内：

1. 根据明确的 `house_id` 重新读取房源；
2. 重新检查所选日期是否与已有订单冲突；
3. 检查通过后插入订单；
4. 冲突或异常时回滚整个事务。

取消订单使用带条件的原子 `UPDATE`，写入条件同时包含：

- 订单号；
- 当前 `user_id`；
- 状态仍为 `confirmed`；
- 入住日期晚于当前日期。

即使 Agent 在确认前后遇到并发状态变化，最终 SQL 仍会重新判断是否允许写入，避免仅依赖模型
早先读取的旧状态。

所有 SQL 使用参数绑定，不把模型生成的字符串直接拼接进查询语句。

## 9. 上下文增长和恢复受到控制

所有 Agent 默认安装两层上下文管理：

- `ContextEditingMiddleware` 在约 8,000 tokens 时清理较早的大型工具结果，保留最近 3 次
  工具使用；
- `SummarizationMiddleware` 在约 12,000 tokens 时总结旧历史，并保留最近 20 条消息原文。

这避免长任务因为网页正文、JSON 结果和历史消息持续累积而超出模型上下文。

Supervisor 还使用上下文投影，只向模型提供用户消息、Supervisor 消息和结构化 handoff 结果，
不会把专业 Agent 的全部内部工具消息重新塞给 Supervisor。这样可以减少内部噪声对下一次路由
判断的干扰。

Agent Server 使用 PostgreSQL checkpoint 保存线程状态。interrupt 恢复后，原有消息、委派记录
和专业执行预算会继续生效，不会因为暂停或上下文压缩重新获得一套调用额度。

## 10. 当前能够达到的稳定效果

当前代码共同保证：

- 路由次数有限，且一次只执行一个专业任务；
- Agent 只能使用职责范围内的工具；
- 模型和工具循环不会无限运行；
- 专业 Agent 通过统一 Schema 返回结果；
- 缺少必要输入或取消确认时可以暂停并恢复；
- 用户身份不能由模型随意指定；
- 预订和取消在数据库层重新校验并原子执行；
- 长上下文会被裁剪或总结；
- 异常路径以明确的拒绝、失败或等待输入状态结束。

这些机制保证的是**执行过程稳定和业务边界稳定**，而不是自然语言字面完全一致，也不能保证
外部模型、搜索服务、网页和数据库永远可用。

当前单元与组件测试共 98 项，覆盖上述主要边界；执行
`.venv/bin/python -m unittest discover -s tests/unit_tests -v` 的结果为全部通过。
