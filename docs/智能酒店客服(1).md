# 多 Agent 租房客服设计说明

## 1. 目标

项目把原来的固定业务子图改写为专业 Agent。Supervisor 仍使用确定性路由，每个专业
Agent 则通过 ReAct 循环自行判断要调用的工具、读取结果并完成用户任务。

## 2. 模块接口

Supervisor 的外部接口保持为 `messages`，身份通过 `configurable.user_id` 传入。
专业 Agent 也只共享消息通道；数据库连接、Store、用户身份和 checkpoint 都通过运行时
注入，不成为模型可自由生成的业务参数。

专业 Agent 的接口很小，复杂行为隐藏在工具实现内：

- `general_qa_agent(messages) -> messages`
- `rental_recommendation_agent(messages) -> messages | interrupt`
- `rental_booking_agent(messages) -> messages | interrupt`
- `order_history_agent(messages) -> messages`
- `order_cancellation_agent(messages) -> messages | interrupt`

## 3. 工具设计

工具按完整业务能力划分，而不是把旧节点机械包装成大量浅工具。例如房源查询只暴露
`search_houses`；Schema 检查、结构化查询规划、SQL 编译、只读校验、重试和执行仍封装
在工具内部。

写操作工具承担最终安全责任：

- `create_booking` 在工具内部重新校验手机号、日期、用户身份和日期冲突；
- `cancel_order` 在工具内部查回当前用户订单，并强制执行一次中断确认；
- 模型即使产生错误参数，也不能扩大表权限或操作其他用户订单。

## 4. 中断与恢复

缺失信息通过 `request_user_input` 工具触发 LangGraph `interrupt`。checkpoint 保存正在
执行的专业 Agent 和工具调用；恢复时使用 `Command(resume=...)` 回到原工具，然后 Agent
读取用户补充结果继续工作，不重新经过 Supervisor 路由。

订单取消不依赖 Agent 声称“用户已经确认”。`cancel_order` 自身始终中断一次，只有恢复
值通过代码确认规则时才执行数据库更新。

## 5. 对照学习

`src/agent/graph`、`node` 和 `state` 保留了原固定图的实现与测试。正式注册的运行图位于
`src/agent/supervisor` 和 `src/agent/agents`。两套实现可以用于比较：

- 固定图：路径显式、可预测性高、节点状态较多；
- 专业 Agent：路径由模型按工具结果动态选择、接口更小、需要更严格的工具保护；
- 两者共享同一批确定性数据库与外部服务适配器。
